# Release runbook and checkpoint checklist

Use from PowerShell 7 in the relevant repository root. Run only the stages authorized for the task. The UI Kit is the MIT-derived core; the website is a separate repository. Re-read both roots' `AGENTS.md` and the UI Kit's `docs/architecture/product-evolution-policy.md` on each new release. The current Bridge phase protects the documented Strelit API, saved configuration, styling, and packaging contract. Review the phase before every major release; it never changes automatically.

Keep an ignored `.tmp/` release record with a row per stage: `status` (`pending`, `running`, `verified`, `unknown`, or `blocked`), target version, repository head and dirty state, command and exit code, observation time, artifact identity or URL, authorization scope, and next action. Checkpoint after each stage. Use the UI Kit's agent ledger for bounded work and recovery; do not treat a partial checkpoint as completed evidence. A new commit invalidates exact-head review and verification, while an unchanged scoped finding closure may be carried forward under repository policy.

The current UI Kit high-risk product profile also runs API demo smoke and browser bundle checks through the definitive `verify:pr` gate; the candidate checks do not replace it. JSR's local dry run rejects an uncommitted tree unless `--allow-dirty` is supplied. Use that flag only for a local preview; the publishing candidate must be clean.

## Read-only commands and safe replay

For exact-version inspection, use `npm view strelit-ui-kit@<version> version dist.tarball dist.integrity --json`, `npx jsr info @strelit/core@<version>`, and `gh release view v<version> --repo dey-joydeep/strelit-ui-kit --json tagName,isDraft,isPrerelease,url,targetCommitish` when authenticated GitHub access is available. Check the tag's peeled commit separately, because `targetCommitish` is not proof of the tag target. Use `gh pr checks <number>` for PR checks and the website commit's check runs for production. CDN URLs are npm-backed; Cloudflare site hosting is a separate channel.

On resume, classify each stage from public read-only evidence and the checkpoint: **verified** only when identity and target match; **pending** only when no external write began; **unknown** when a write may have happened but cannot yet be proven; **blocked** when the observed artifact conflicts. Never replay a publish, tag creation, merge, or deployment from a locally failed command alone. Re-run local checks when source changes; re-request authorization if the approved version, destination, or artifact changed.
